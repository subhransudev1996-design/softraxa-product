## Decisions (confirmed with owner)

- **Scope:** Full V1, mobile first — DB schema → Flutter customer app → Next.js admin panel.
- **Backend:** Existing Supabase cloud project. Migrations are written as numbered SQL files in `supabase/migrations/`; owner runs them in the Supabase SQL editor (or via CLI later). App uses `.env` for `SUPABASE_URL` / `SUPABASE_ANON_KEY`.
- **Offline:** Online-first with offline **billing fallback only** (PRD §7.10). Products/customers cached locally; offline bills saved with provisional numbers and synced on reconnect.
- **Flutter stack:** Riverpod 3 (state), go_router (navigation), supabase_flutter, drift 2.29 (local cache/offline queue — 2.31+ needs a newer Dart SDK), mobile_scanner (camera barcode), pdf + printing (invoices), print_bluetooth_thermal + esc_pos_utils_plus (thermal), excel (import/export).
- **Admin stack:** Next.js 16 (App Router) + Tailwind + supabase-js; service-role key used only in the `/api/clients` route handler; auth guard in the `(dashboard)` server layout (no middleware).
- **Media (added 2026-07-03):** ImageKit instead of Supabase Storage. Upload signature comes from the `get_imagekit_auth` RPC (migration 0012) so the private key never ships in the app; public key is embedded in `apps/mobile/lib/core/imagekit.dart`. Used for business logos; product image upload removed from the product form for now (DB column kept). Migration 0011 (storage buckets) is now optional.
- **GST math:** POS prices are GST-inclusive; tax back-calculated per line, bill discount applied post-tax so client totals equal the server `create_invoice` formula (locked by unit test).
- **Credit limits (2026-07-04):** optional `credit_limit` (nullable numeric) added to `customers` and `suppliers` (migration 0013). Set in the add/edit dialogs; blank = no limit. Enforced as a soft warning, not a hard block: checkout sheet (customer) and purchase form (supplier) show an inline orange banner and a confirm-to-proceed dialog when the projected due would exceed the limit; customer/supplier list and detail screens flag accounts already over their limit.
- **Payment-status enum cast bug (fixed 2026-07-04, migration 0014):** `create_purchase`, `record_customer_payment` and `record_supplier_payment` inlined a bare `case when ... then 'paid' ... end` directly into an INSERT/UPDATE, which Postgres resolves to `text`, not the `payment_status` enum — failed with "column is of type payment_status but expression is of type text" on any partial/unpaid purchase or due payment. `create_invoice` never had this bug because it assigns the same CASE to a `public.payment_status`-typed variable first. Fix: cast the inline CASE expression explicitly (`(...)::public.payment_status`) in all three functions; also corrected in 0008_functions.sql itself for fresh installs.
- **Split payments in POS (2026-07-04, migration 0015):** `create_invoice` now accepts an optional `payments` array in the payload — `[{mode, amount}, ...]` — and inserts one `invoice_payments` row per entry instead of a single row; falls back to the old single `paid_amount`/`payment_mode` fields when absent (offline-queued payloads from before this change keep working). No enum/schema change: `invoices.payment_mode` is set to the one mode used, or `'other'` when 2+ distinct modes were used in the same bill. Checkout sheet (`checkout_sheet.dart`) has a "Split payment" toggle that swaps the single cash/UPI/card/credit chips for a repeatable list of {mode, amount} rows (e.g. ₹500 cash + ₹500 UPI); any shortfall still becomes customer due exactly like a normal partial payment, and the credit-limit warning uses the same combined due.
- **List/detail screens with search + filters (2026-07-04):** Invoices, Sale returns, Stock, Purchases, Suppliers, Customers all gained search and/or date filters this session — no DB changes needed, all client/query-side. Purchases uses quick presets (All/Today/Yesterday/This week/This month) instead of a free-range picker; Suppliers/Customers gained a balance filter (All/Has balance/Cleared) via `due_amount` comparisons.
- **Purchase returns UI (2026-07-04):** the `create_purchase_return` RPC and `PurchaseReturnFormScreen` already existed but were only reachable from one specific purchase's detail page, with no list/detail screens or nav entry — effectively invisible. Added `PurchaseReturnsScreen` (list, search + date filter, "New return" FAB with its own purchase picker so you don't need to open a purchase first) and `PurchaseReturnDetailScreen` (line items + settlement), mirroring the existing Sale Returns screens. Wired at `/purchase-returns` and `/purchase-returns/:id`, plus a "Purchase returns" tile in More → Inventory. No DB/RPC changes — purely additive UI.
- **Checkout customer confirmation card (2026-07-04):** the POS checkout sheet computed with `cart.customer` (due/credit-limit checks) but never displayed who the bill was actually for — customer selection only happened back on the POS screen's own row. Added a "Customer" card at the top of `checkout_sheet.dart` (name, phone, address, current due, credit limit if set) with inline Select/Change/Remove actions (reuses `showCustomerPicker` from `customer_picker.dart`), so the customer can be confirmed or changed without leaving checkout. Purely additive UI, no provider/schema changes.
- **Fully custom variant attributes (2026-07-04):** `variant_sheet.dart`'s "Add variant" sheet used to show the business-type template fields (e.g. Model/RAM/Storage/Color for mobile) as fixed, non-removable labels with only the value editable — "Add custom attribute" could only append more fields via a separate dialog. Reworked so every row (including the seeded template defaults) is a plain {field name, value} pair, both directly editable inline, with a remove button per row; "Add field" just appends a blank row. `VariantDraft.attributes` (a plain `Map<String,String>`) and the DB shape are unchanged — this was purely a UI/state rework (`_AttrRow` list instead of the old fixed `_fields`/`_attrs` map). Editing an existing variant now shows exactly its saved attributes (no forced re-merge of template defaults the user may have deliberately removed).
- **Out-of-stock warning in POS (2026-07-04):** tapping a 0-stock product in the POS search results (or an exact barcode/wedge-scanner match) silently added it to the bill with no signal at all. `pos_screen.dart`'s `_addToCart` now checks `current_stock` (product or variant) before adding; if it's ≤0 it shows a dialog with **Cancel** / **Add stock first** (opens `showAdjustStockSheet` inline, then re-checks live stock via a fresh query before deciding whether to auto-add) / **Add anyway** (soft-block, same pattern as the credit-limit warnings — owners can still knowingly oversell). The continuous camera-scan flow (`scan_screen.dart`) isn't blocked with a dialog (would break rapid scanning) but its snackbar now turns orange and says "— out of stock!" instead of silently reading "Added: X".
- **FIFO due-payment allocation bug (fixed 2026-07-04, migration 0018):** paying down a customer's/supplier's *overall* due from the Customer/Supplier detail screen (which only asks for amount + mode, not "which invoice") correctly reduced `customers.due_amount`/`suppliers.due_amount`, but never touched the actual `invoices`/`purchases` rows — so a specific invoice kept showing "unpaid" with a "Record payment" button forever even though the customer's aggregate balance was already clear. `record_customer_payment`/`record_supplier_payment` already handled this fine when called *with* an explicit invoice/purchase id (the button on the invoice/purchase's own detail page) — the gap was only the no-id path. Fixed by having that path settle the oldest outstanding invoices/purchases first (FIFO by date) until the payment amount is used up, updating each one's `paid_amount`/`payment_status` (and inserting proper `invoice_payments` rows) along the way. Also added `ref.invalidate(invoicesProvider)` / `ref.invalidate(purchasesProvider)` to the customer/supplier detail screens' payment handlers so the Invoices/Purchases list screens pick up the change immediately too.
- **Cart quantity could exceed stock (fixed 2026-07-04):** the earlier out-of-stock warning only checked a fresh add against `current_stock <= 0` — it didn't account for quantity already in the cart, so tapping a search result repeatedly (or re-scanning the same barcode, or using the qty stepper's `+`, or the manual qty-edit dialog) could silently push cart quantity past actual stock (e.g. stock=4, cart qty=6). Added `CartNotifier.qtyInCart(productId, variantId)` (sums across lines, since serial-tracked items get one line per unit rather than merging) and now check *projected* quantity, not just raw stock, everywhere quantity can increase: `pos_screen.dart`'s `_addToCart` (search tap / wedge-scan exact match) and a new `_changeQty` wrapper used by both the qty stepper and the edit-line dialog — same warn-with-override pattern as the original out-of-stock dialog (Cancel / Add stock first / Add anyway; the Add-stock branch opens `showAdjustStockSheet` inline using a minimal product/variant map built from the `CartLine`'s own fields, then refreshes that line's stock snapshot via a new `CartNotifier.updateAvailableStock` — `CartLine.availableStock` was made mutable for this). The continuous camera-scan flow (`scan_screen.dart`) stays non-blocking (dialogs would break rapid scanning) but its snackbar now says "only N in stock, billing M!" instead of just "Added: X" whenever a scan pushes the cart over stock.
- **Stock-warning dialog styling (2026-07-04):** the 3-button Cancel/Add-stock-first/Add-anyway dialog looked inconsistent — only the FilledButton stretched full-width (from the app theme's `minimumSize: Size.fromHeight(52)`), while Cancel and the OutlinedButton stayed intrinsic-width, because AlertDialog's default `actions:` overflow layout doesn't stretch buttons uniformly once 3 don't fit on one row. Extracted a shared `_showStockDialog()` in `pos_screen.dart` that puts all three buttons in `content` (a stretched `Column`) instead of `actions`, giving all three consistent full width and even 8px spacing; both call sites (`_confirmStockIssue` for adding, `_changeQty` for qty changes) now use it so they stay visually identical.
- **Ledger entries didn't show discount context (2026-07-04):** the customer/supplier ledger list showed a bare invoice/purchase total (e.g. "+ ₹90.00") with no indication that ₹10 of a ₹100 base price was a discount — confusing next to the aggregate "Outstanding due" figure above it, which is a running balance across every ledger entry and isn't meant to reconcile against any single line. `customerLedgerProvider`/`supplierLedgerProvider` now also select `subtotal`/`discount_amount`; both detail screens' ledger rows (extracted into a shared `_ledgerTile` helper in each file) show a small "₹X discount applied" note under the date whenever an invoice/purchase had one. The invoice/purchase detail screens already broke out Subtotal/Discount/Total clearly — this just extends that same clarity to the summary ledger view instead of requiring a tap-through.
- **No payment button when nothing is due (2026-07-04):** the Customer detail screen always showed a payment button — "Receive payment" (filled) when `due > 0`, or a redundant "Record payment" (outlined) even at zero/cleared due. Removed the zero-due button entirely; it now only appears when there's an actual due to collect. (Left the Supplier screen's "Pay supplier" as-is — it's paired side-by-side with "New purchase" in one row, a different, intentional layout not part of this request.) Also confirmed (no code change needed) that the "Receive due payment" dialog already closes immediately on tapping Receive/Record — `Navigator.pop` runs synchronously in the button's `onPressed`, before the RPC call, in both the customer-detail and invoice-detail payment dialogs.
- **Category/service dropdowns empty until you added a new one (fixed 2026-07-04):** the Add Expense dialog's Category dropdown, and the Job Card "Add labor" dialog's "from service catalog" dropdown, populated via `ref.read(xProvider).value ?? []` — a synchronous read of an `autoDispose` `FutureProvider` that nothing else in either screen ever `watch`es. First time you open either dialog, the provider hadn't been triggered/resolved yet, so `.value` was still `null` → empty dropdown. Adding a new category/service worked because *that* path correctly did `await ref.refresh(...).future`. Fixed both dialogs to `await ref.read(xProvider.future)` (wrapped in try/catch, matching the app's error-handling convention) instead of reading a possibly-unresolved synchronous snapshot — same fix applied to `expenses_screen.dart` and `job_card_detail_screen.dart`. (Checked for the same pattern elsewhere: `pos_screen.dart`'s barcode-submit handler also does a bare `.value ?? []` read, but that one is legitimately fine — `posProductsProvider` is continuously `watch`ed by the same screen's own `build()`, so it's always warm by the time a scan can happen, and staying synchronous there is intentional so scanning doesn't wait on a network round-trip.)

Bottom bar: 4 tabs + center gradient "New Bill" FAB (`home_shell.dart`). Rolled out to every screen (POS, products, invoices, purchases, customers, suppliers, stock, expenses, reports, import, offline bills, support, auth, onboarding) — canvas background, IconChip/InitialsAvatar leading icons, consistent AppColors tokens instead of raw Material colors. Camera scan screen keeps its black chrome by design, with crimson corner brackets on the viewfinder.

- **Desktop dashboard density fix (2026-07-04):** first real look at the desktop build (screenshotted the running window via `PrintWindow`, since there's no way to eyeball a native Windows app otherwise) showed the dashboard's stat-tile row using a hardcoded `GridView.count(crossAxisCount: 2, childAspectRatio: 1.72)` sized for phone width — stretched to desktop width this produced two huge, mostly-empty ~500×290px boxes per row instead of compact KPI tiles, the single biggest reason the desktop UI didn't read as a "real" desktop app (reference: Vyapar Desktop's dense stat-tile rows). Fixed by wrapping the grid in a `LayoutBuilder` that derives `crossAxisCount` from available width (`(width/220).floor().clamp(2,4)`) and computes `childAspectRatio` from a fixed target tile height (92px) rather than a hardcoded ratio — same code path renders identically on mobile (still 2 columns, ~97px tall, matching prior behavior almost exactly) and now renders as a compact single row of up to 4 tiles on desktop. Also wrapped everything below the full-bleed purple hero header in a `Center` + `ConstrainedBox(maxWidth: 1400)` so the body doesn't stretch uncomfortably wide on very large monitors (no-op on phone widths). Only `dashboard_screen.dart` changed — it was the only screen using a `GridView`; other list screens (Products, Invoices, Customers, etc.) use plain `ListView.separated` card tiles, which don't have the same "giant empty box" failure mode but also aren't table-dense like Vyapar's real desktop grids — upgrading those to proper multi-column desktop tables is a separate, larger follow-up not done in this pass.

- **Invoice-tile overflow, actually fixed (2026-07-04):** the previous same-day "fix" (`mainAxisSize.min` + more `contentPadding`) turned out not to work — user re-reported the identical "BOTTOM OVERFLOWED BY 1.00 PIXELS" banner on every row. Root cause, found via `flutter run -d windows` console output (not screenshots — screenshots of this specific bug were misleadingly showing blank space where the trailing amount/status should be, apparently a `PrintWindow` capture quirk with Flutter's GPU-composited surface, not a real rendering gap): `ListTile.trailing` is given a **fixed internal max-height (~40px) independent of `contentPadding`** — padding changes the tile's overall height/spacing but never touched that fixed trailing-slot constraint, so the 2-line trailing content (amount + `StatusChip`, ~41px under Windows font metrics) kept overflowing by exactly 1px no matter how much padding was added. Real fix: stopped using `ListTile` for `_InvoiceTile` entirely and rebuilt it as a plain `InkWell` + `Row` with `mainAxisSize.min` columns — sizing purely from content instead of an invisible fixed slot, which structurally cannot reproduce this failure mode. Same pattern already established in this codebase for the earlier stock-warning-dialog `actions:` sizing bug (PRD session 2026-07-04 above): when a Material widget's internal layout assumptions don't fit a custom design, build the row manually rather than fighting the widget's internals with padding/size tweaks. Verified via console (no `OVERFLOW`/`RenderFlex` exceptions on a fresh `flutter run -d windows`), not just visually.
- **Purchase return could drive stock negative (fixed 2026-07-04, migration 0019):** reported as "purchased 5, returned 5, but it let me return when there was no stock and qty went negative." Root cause: `create_purchase_return` (0008_functions.sql) inserted a negative `stock_movement` for the returned quantity with **zero validation anywhere** — not in the RPC, not in the `apply_stock_movement()` trigger, not in the client. If some of the purchased qty had already been sold via POS before the return was recorded (current_stock < purchased qty), returning the full originally-purchased amount was silently allowed and drove `current_stock` negative. Contrast `create_sale_return`, which only ever *adds* stock back — safe by construction, hence no check was ever needed there; purchase return is the one risky direction. Unlike POS overselling (a legitimate soft-warn/backorder case), there's no valid business reason to return more physical stock than the shop currently holds, so this is a **hard block**, not a warn-with-override: migration 0019 redefines `create_purchase_return` to check `current_stock` (product or variant) against the requested return quantity for every line *before* writing anything, and `raise exception`s with a clear message if it's short. ## Runbook (for the owner)

1. Open your Supabase project → SQL editor → run each file in `supabase/migrations/` in numeric order (0001 → 0025). **The current app build requires 0020, 0021 and 0022** (POS/purchase product queries select the new columns, and the purchase form now sends a `round_off` field to `create_purchase`); without 0020/0021, POS falls back to the offline product cache and the purchase product picker shows an error. Without 0022, purchases still save fine (the old `create_purchase` just ignores the extra `round_off` payload field), but the purchase total won't include rounding and the "Round off" row will always show ₹0. **0023** fixes a dormant sales-report bug (no user-visible change without it). **0024 is required** for sale/purchase returns to reject over-returning the same invoice/purchase twice. **0025 is required** for the new "Edit bill" invoice-editing feature — without it, tapping "Edit bill" and saving will fail with an RPC-not-found error.
2. Copy `apps/mobile/.env.example` → `apps/mobile/.env`, paste your `SUPABASE_URL` and `SUPABASE_ANON_KEY`.
3. `cd apps/mobile && flutter pub get && flutter run`
4. Admin panel: copy `apps/admin/.env.example` → `apps/admin/.env.local` (also needs the service-role key), then `npm install && npm run dev`.
5. Create your own admin login: sign up once (via the mobile app or Supabase dashboard), then in the SQL editor run
   `update public.profiles set role = 'admin' where email = '<your-email>';` — that account can now log in to the admin panel.
